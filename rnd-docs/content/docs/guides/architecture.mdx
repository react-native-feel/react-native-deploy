## What touches your secrets

| Asset | Local | In transit | On remote | After build |
| --- | --- | --- | --- | --- |
| ASC `.p8` | `~/.appstoreconnect/AuthKey_*.p8` (mode 600) | SSH-encrypted | `/tmp/AuthKey.p8` (mode 600) | Deleted |
| ASC keychain entry | macOS keychain | — | `asc auth login --bypass-keychain` | Logged out |
| `.p12` distribution cert | Not on local | — | Imported into `rn-deploy-build.keychain` | Keychain destroyed |
| `.mobileprovision` | Not on local | — | `~/Library/MobileDevice/Provisioning Profiles/` | Stays installed (multi-build reuse) |
| Source code | Local checkout | — | `~/build-workspace` (cleaned each build) | Cleaned |
| `.ipa` artifact | Downloaded to local cwd | SSH-encrypted | `~/build-workspace/build/export/` | Deleted with workspace |

## Why a dedicated keychain

We never touch the host's `login.keychain`. The build keychain (`rn-deploy-build.keychain`) is:

- Created per build
- Unlocked for 6 hours (`-lut 21600`)
- Added to the user's search list so `codesign` can find it
- Destroyed in `teardownSigning()`, success or failure

This means even if multiple builds run on the same host (CI persistence), they don't interfere with each other.

## Why tmux

`xcodebuild` builds can take 20+ minutes. SSH sessions over flaky networks (corporate VPN, cafe wifi, CI runners with idle timeouts) drop. Running the build inside a detached tmux session means:

- The build keeps running if the SSH connection dies
- `rn-deploy build --resume` reconnects to the same session
- The full log is also `tee`'d to `/tmp/rn-deploy-build.log` for post-mortem

## How EAS compatibility actually works

`src/config/expo-loader.js` is the only file that knows about Expo's config shape. It:

1. Discovers `eas.json` / `app.json` / `app.config.{js,ts}` in the project directory
2. For dynamic configs, shells out to `npx --no-install expo config --type public --json` (Expo's own resolver — we don't reimplement it)
3. Maps EAS field names to our internal shape (see [EAS compatibility](/docs/eas-compatibility))
4. Returns a config object with the same structure as `deploy.config.json` would produce

`loader.js` then layers the (optional) `deploy.config.json` overlay on top via shallow + targeted deep merges. Nothing downstream knows or cares whether the config came from EAS or from `deploy.config.json` — they're isomorphic.

## Why the asc CLI

The whole signing/submission story stands on the [`asc`](https://github.com/rork/asc) CLI from Rork. We use it because:

- Native macOS keychain integration for ASC API keys
- `asc signing fetch` / `asc signing sync` solve the cert-distribution problem
- `asc profiles local install` correctly drops profiles into Xcode's expected directory
- `asc builds upload` + `asc publish testflight` replace the old `iTMSTransporter` mess
- It's a single-binary install (`brew install asc`)

If you'd rather not depend on `asc`, the same primitives are available via raw ASC API calls + `security` commands — but it's a lot more code for the same outcome.

## Contributing

The codebase is plain ESM JavaScript, no transpile step. Run the CLI directly via `node bin/rn-deploy.js` from the repo root. There's no test suite yet — adding one (Vitest + mocked SSH) is a welcome contribution.

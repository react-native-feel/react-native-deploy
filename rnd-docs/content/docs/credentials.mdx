`rn-deploy` never stores your App Store Connect credentials in plaintext config files. Instead, it delegates to the [`asc`](https://github.com/rork/asc) CLI, which uses the macOS keychain by default.

## How credentials are resolved

When `rn-deploy build` or `rn-deploy submit` needs ASC credentials, it walks this chain:

<Steps>

<Step>

### `deploy.config.json` `asc.*` (legacy)

If your config has `asc.keyId`, `asc.issuerId`, and `asc.privateKeyPath`, those win. This path exists for backwards compatibility and CI scenarios where you bake the key into a controlled file path.

</Step>

<Step>

### Environment variables

`ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_PRIVATE_KEY_PATH` together. Use these in CI:

```bash
export ASC_KEY_ID="ABCD123XYZ"
export ASC_ISSUER_ID="01234567-89ab-cdef-0123-456789abcdef"
export ASC_PRIVATE_KEY_PATH="$RUNNER_TEMP/AuthKey.p8"
echo "$ASC_KEY_BASE64" | base64 -d > "$ASC_PRIVATE_KEY_PATH"
rn-deploy build --profile production
```

</Step>

<Step>

### `asc` keychain

If neither of the above is set, `rn-deploy` asks `asc auth status --output json` for the active profile and uses those values. The `.p8` file path is discovered by checking these locations in order:

1. The path `asc` reports
2. `~/.appstoreconnect/AuthKey.p8`
3. `~/.appstoreconnect/AuthKey_<keyId>.p8`
4. `~/private_keys/AuthKey_<keyId>.p8`

If the `.p8` isn't found, the build fails fast with a clear error.

</Step>

</Steps>

## Why we still need the `.p8` locally

`asc` stores the key material *encrypted* in the macOS keychain, but `rn-deploy` needs to **upload the actual `.p8` to the remote Mac** so it can authenticate there too. We can't pull the key bytes back out of asc's keychain entry programmatically — that's by design.

So: keep the `.p8` at one of the discoverable paths above, with mode `600`. It's not a secret beyond the value of the key itself, but it's worth treating like any other private key.

```bash
chmod 600 ~/.appstoreconnect/AuthKey_*.p8
```

## Setting up credentials

```bash
rn-deploy credentials configure
```

You'll be prompted for:

| Prompt | Source |
| --- | --- |
| Friendly name | Free-form label, default `rn-deploy` |
| Key ID | From [appstoreconnect.apple.com/access/integrations/api](https://appstoreconnect.apple.com/access/integrations/api) — 10-character ID next to your key |
| Issuer ID | Same page, top of the API Keys tab — UUID |
| `.p8` path | Where you downloaded the key file |

Internally this runs:

```bash
asc auth login \
  --name rn-deploy \
  --key-id ABCD123XYZ \
  --issuer-id 01234567-... \
  --private-key ~/.appstoreconnect/AuthKey_ABCD123XYZ.p8 \
  --network
```

`--network` does a lightweight API call to confirm the key actually works before storing it.

## Inspecting credentials

```bash
rn-deploy credentials status
```

```text
ℹ Active profile: rn-deploy
ℹ Key ID:         ABCD123XYZ
ℹ Issuer ID:      01234567-89ab-cdef-0123-456789abcdef
✔ Resolution source: keychain
ℹ Local .p8 path:    /Users/you/.appstoreconnect/AuthKey_ABCD123XYZ.p8
```

The "Resolution source" tells you which layer of the chain provided the credentials — useful for debugging CI runs.

## Multiple accounts / profiles

If you ship apps for multiple teams (agency, side projects, day job), register each under its own asc profile name and switch between them:

```bash
rn-deploy credentials configure   # First account, name it "personal"
rn-deploy credentials configure   # Second account, name it "client-acme"

rn-deploy credentials switch client-acme
rn-deploy build --profile production    # uses client-acme key
```

Under the hood this calls `asc auth switch --name <profile>`.

## Removing credentials

```bash
rn-deploy credentials logout            # default profile
rn-deploy credentials logout client-acme
```

Removes the keychain entry. The `.p8` file on disk is left in place — delete it manually if you want it gone.

## CI / unattended environments

In CI you usually don't want a macOS keychain in the loop. Use the env-var path:

<Tabs items={["GitHub Actions", "GitLab CI", "Generic"]}>

```yaml tab="GitHub Actions"
jobs:
  build:
    runs-on: macos-14
    steps:
      - uses: actions/checkout@v4
      - run: npm i -g rn-deploy
      - name: Build
        env:
          ASC_KEY_ID: ${{ secrets.ASC_KEY_ID }}
          ASC_ISSUER_ID: ${{ secrets.ASC_ISSUER_ID }}
          ASC_PRIVATE_KEY_PATH: ${{ runner.temp }}/AuthKey.p8
          ASC_P12_PASSWORD: ${{ secrets.ASC_P12_PASSWORD }}
        run: |
          echo "${{ secrets.ASC_KEY_BASE64 }}" | base64 -d > "$ASC_PRIVATE_KEY_PATH"
          chmod 600 "$ASC_PRIVATE_KEY_PATH"
          rn-deploy build --profile production --auto-submit
```

```yaml tab="GitLab CI"
build:ios:
  tags: [macos]
  variables:
    ASC_KEY_ID: $ASC_KEY_ID
    ASC_ISSUER_ID: $ASC_ISSUER_ID
    ASC_PRIVATE_KEY_PATH: $CI_BUILDS_DIR/AuthKey.p8
    ASC_P12_PASSWORD: $ASC_P12_PASSWORD
  script:
    - echo "$ASC_KEY_BASE64" | base64 -d > "$ASC_PRIVATE_KEY_PATH"
    - chmod 600 "$ASC_PRIVATE_KEY_PATH"
    - rn-deploy build --profile production --auto-submit
```

```bash tab="Generic"
export ASC_KEY_ID="ABCD123XYZ"
export ASC_ISSUER_ID="01234567-..."
export ASC_PRIVATE_KEY_PATH="/secure/path/AuthKey.p8"
export ASC_P12_PASSWORD="..."

rn-deploy build --profile production --auto-submit
```

</Tabs>

## What gets uploaded to the remote Mac

For every build, `rn-deploy` uploads exactly one credential to `/tmp/AuthKey.p8` (mode 600) and runs `asc auth login --bypass-keychain` there. After the build, both the file and the asc session are torn down.

The remote Mac never has long-lived access to your account — even if the host is compromised between builds, your key isn't sitting there.
